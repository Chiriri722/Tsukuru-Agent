확인했습니다. **Tsukuru Agent에는 YSB Game Editor의 “문맥을 보면서 번역하고 검수하는 기능”을 우선 반영하고, RPGMakerDecrypter는 “구형 포맷 이해·호환성 비교·미지원 형식 진단”의 참고 대상으로 활용하는 방향이 가장 적합합니다.** 세 저장소를 통째로 합치기보다는, Tsukuru의 기존 검증·적용 구조 위에 필요한 기능을 추가하는 편을 권합니다.

특히 실제 코드를 확인해 보니, **Tsukuru에 이미 있는 기능을 새로 도입할 필요는 없었습니다.** MV/MZ 자산 복호화·재암호화, 프로젝트 변환, 대사 블록 단위의 일부 문맥 검사가 이미 구현되어 있습니다. 반대로 YSB에서는 이름만 남아 있고 실제로는 제거된 기능도 있어, README와 파일 이름만 비교하면 잘못 판단하기 쉬운 부분이 있었습니다.

각 저장소의 트리와 주요 구현 파일을 확인했습니다. **이번 평가는 정적 코드 검토입니다.** 로컬 빌드, 실제 게임 실행, 세 프로그램을 같은 게임에 적용하는 비교시험까지 수행한 것은 아니므로, 아래의 구현상 관찰과 실제 실행으로 검증해야 할 사항을 구분하겠습니다.

**따라서 “어느 프로그램이 더 많은 기능을 갖췄는가”보다는, “번역 작업의 어느 단계를 담당하는가”로 비교해야 합니다.**

## 2. Tsukuru Agent는 이미 어디까지 구현되어 있는가

### 2-1. 다른 두 저장소보다 엔진·컨테이너 범위가 넓습니다

현재 Tsukuru의 지원 범위는 RPG Maker MV/MZ에 그치지 않고 Wolf RPG, TyranoScript, 제한된 GDevelop 번역 경로까지 포함합니다. 다만 이것을 “모든 엔진을 모든 컨테이너에서 동일하게 지원한다”로 이해하면 안 됩니다.

예를 들어 호환성 문서에서는 RPG MV/MZ의 Electron ASAR 처리를 지원하지만, **ASAR 내부의 Wolf/Tyrano는 진단 단계**로 구분합니다. `package.nw`도 ZIP, 디렉터리형, 실행 파일 뒤에 붙은 형태에 따라 지원 수준과 실험 옵션이 다릅니다. GDevelop 역시 임의의 JavaScript 전체가 아니라 허용된 정적 텍스트 범위를 중심으로 처리합니다. 

반면 YSB의 실제 번역·저장 경로는 **MV/MZ JSON 구조**를 기준으로 합니다. XP/VX/VX Ace와 RPG Maker 2000/2003을 감지하는 코드는 있지만, 그 목적은 지원하는 것처럼 열기 위한 것이 아니라 “다른 형식이므로 별도 지원이 필요하다”는 정확한 오류를 보여 주는 것입니다.  

### 2-2. 복호화·재암호화는 이미 있습니다

`tsukuru-agent/src/js/rpgmv/fileCrypto.ts`에는 다음 함수가 있습니다.

- `DecryptDir`: 이미지·오디오 자산을 복호화합니다.
- `EncryptDir`: 작업한 이미지·오디오 자산을 다시 암호화합니다.

`DecryptDir`은 `System.json`의 키 형식을 검사하고, 자산 경로의 심볼릭 링크·정션을 차단하며, 정렬된 파일 목록을 대상으로 임시 작업 공간에서 처리한 뒤 결과를 반영합니다. 취소 신호도 검사합니다. 

이 기능은 사용되지 않는 보조 파일로만 존재하는 것도 아닙니다. `RpgMakerService.ts`의 추출 경로에서 `decryptImg`·`decryptAudio` 옵션에 따라 호출하고, 적용 경로에서는 재암호화 후 출력 검증을 수행합니다. 

**따라서 Decrypter를 붙여서 “MV/MZ 복호화를 새롭게 지원한다”는 개발 방향은 중복입니다.** 오히려 기존 구현의 호환성·오류 처리·회귀시험을 보강하는 쪽이 맞습니다.

### 2-3. 프로젝트 변환도 있습니다. 다만 CLI 핵심 서비스와는 분리되어 있습니다

`projectConvert.ts`는 별도 출력 폴더에 게임을 복사하고, 자산을 처리한 뒤 `Game.rpgproject` 또는 `game.rmmzproject`를 생성합니다. 출력 경로 중첩 검사와 `WorkspaceTransaction`도 사용합니다.

그러나 이 코드는 Electron의 `app`, `dialog`, 창 객체에 의존합니다. 즉, **기능은 존재하지만 에이전트가 호출하기 좋은 순수 서비스 형태로 완전히 분리된 것은 아닙니다.** 아키텍처 문서도 프로젝트 변환과 외부 번역을 기존 GUI 호환 경로로 구분합니다.  

이 부분을 개선한다면 외부의 C# 구현을 끌어오기보다, **기존 변환 로직에서 폴더 선택·알림·진행률 UI를 떼고 서비스 계층으로 내리는 작업**이 자연스럽습니다.

### 2-4. “문맥을 전혀 모르는 추출기”도 아닙니다

`messageQuality.ts`는 원본 `Backup`에서 이벤트 목록을 읽고, 같은 들여쓰기 수준의 `101` 메시지 시작 명령과 연속된 `401` 대사 명령을 묶습니다. 이 블록 안에서 따옴표 균형과 스타일을 검사하며, 정상적인 메시지 헤더를 찾지 못하면 문맥 확인 불가 경고를 만듭니다. 

다만 이것은 **문맥 구조를 이용한 기계적 검사**입니다. 등장인물의 말투, 직전 선택지, 장면의 의미, 화면에서의 잘림까지 판단하는 기능과는 다릅니다.

YSB에서 가장 가치 있게 가져올 부분은 바로 이 간격을 메우는 기능입니다.

## 3. RPGMakerDecrypter: 무엇이 다르고 무엇을 참고할 만한가

### 3-1. 가장 큰 차별점은 XP/VX/VX Ace 아카이브 처리입니다

Decrypter는 `.rgssad`, `.rgss2a`, `.rgss3a` 계열 아카이브와 MV/MZ 암호화 파일을 처리합니다. 원래 프로젝트를 “최선의 추정”으로 재구성하는 기능도 제공하지만, 작성 당시 프로젝트를 완벽하게 복원한다고 설명하지는 않습니다. 

여기서 중요한 경계는 다음과 같습니다.

> **구형 RPG Maker 아카이브를 풀 수 있다는 것과, 구형 RPG Maker 게임을 안전하게 번역할 수 있다는 것은 별개입니다.**

Decrypter의 RGSS 처리기는 아카이브에 들어 있는 파일의 이름·위치·크기 등을 읽고 파일 데이터를 복호화하여 출력합니다. 이것만으로 `.rxdata`, `.rvdata`, `.rvdata2` 안의 대사와 데이터베이스를 Tsukuru의 manifest에 대응시키거나, 번역 후 원래 구조로 안전하게 되돌리는 기능까지 생기지는 않습니다. YSB 역시 이러한 구형 데이터 형식을 MV/MZ JSON과 분리해서 다룹니다.  

Tsukuru에 구형 엔진 번역을 추가하려면 별도의 데이터 파서, 텍스트 위치 식별, 인코딩 처리, 재삽입, 구조 보존 검사가 필요합니다. **Decrypter 연동 하나로 완료되는 소규모 기능으로 잡으면 안 됩니다.**

### 3-2. MV/MZ 쪽에서 특별히 더 강력한 키 복구를 제공하는 것은 아닙니다

확인한 `EncryptionKeyFinder.cs`는 입력 디렉터리 아래에서 `System.json`을 찾아 `encryptionKey`를 읽습니다. 키가 없거나 유효하지 않으면 오류를 반환합니다.

따라서 이 저장소를 “Tsukuru에서 열리지 않는 온갖 보호 게임도 해결해 주는 범용 복호화 도구”로 볼 근거는 없습니다. **확인한 MV/MZ 키 획득 경로는 Tsukuru와 마찬가지로 게임의 `System.json`에 의존합니다.**  

### 3-3. 그대로 외부 실행 도구로 연결하기 전에 고쳐야 할 동작이 있습니다

#### ① MV/MZ의 `--output` 문서와 실제 처리 경로가 일치하지 않습니다

README는 MV/MZ에 `--output`을 주어 다른 디렉터리로 추출하는 예시를 보여 줍니다. 하지만 실제 `MVMZHandler.cs`에서는 작업 디렉터리를 입력 경로로 시작하고, **프로젝트 재구성 옵션을 켰을 때만 출력 경로로 변경합니다.**  

이후 `DirectoryFilesDecrypter.cs`는 각 암호화 파일이 있던 디렉터리에 확장자를 바꾼 결과를 씁니다. 따라서 확인한 코드대로라면 일반 MV/MZ 복호화에서는 `--output`만 지정해도 결과가 입력 폴더에 만들어질 수 있습니다. 기본 경로에서 암호화 원본을 무조건 삭제한다는 뜻은 아니지만, **입력 폴더가 변경되지 않는다는 보장은 성립하지 않습니다.** 

이것은 실제 실행으로 재현한 결과가 아니라, 호출 인자와 출력 경로를 추적한 정적 검토 결과입니다. 그래도 Tsukuru의 원본 보존 원칙과 충돌하기에 충분한 도입 주의점입니다.

#### ② 아카이브 경로 처리도 Tsukuru의 기준으로 다시 검증해야 합니다

`ArchiveFileNameUtils.cs`는 경로를 나누고 잘못된 파일명 문자를 제거하지만, 확인한 코드에서는 `..` 경로 요소를 명시적으로 거부하지 않습니다. `RGSSAD.cs`의 출력 코드도 결합된 경로가 최종 출력 루트 안에 남는지 다시 검사하지 않습니다.  

**파일명 정리와 경로 이탈 방지는 같은 검사가 아닙니다.** 이 부분은 악성 아카이브를 이용한 전체 재현까지 수행한 것은 아니지만, 파서를 가져올 때 반드시 보강해야 할 안전 경계입니다.

또한 단순히 “임시 폴더에 복사한 다음 실행”하는 것만으로 경로 이탈 문제가 해결되지는 않습니다. 출력 경로 검사 자체를 보강하거나, 프로세스가 쓸 수 있는 위치를 실제로 제한해야 합니다.

#### ③ CLI라는 점만으로 Tsukuru와 같은 에이전트 인터페이스는 아닙니다

Decrypter의 CLI는 사람이 읽는 문자열을 `Console.WriteLine`으로 출력하고, 오류를 별도 로그 파일로 남깁니다. Tsukuru처럼 최종 JSON 결과와 진단 로그를 분리한 계약은 아닙니다. 

연동한다면 결과 파일 목록·종료 상태·부분 실패·오류 코드를 별도로 정규화해야 합니다. 하지만 MV/MZ 기능이 이미 중복된다는 점을 고려하면, 이 어댑터를 먼저 만들 실익은 크지 않습니다.

### 3-4. 권장 활용: 실행 의존성보다 포맷 참고와 시험 기준

제가 권하는 활용 방식은 다음 세 가지입니다.

| 활용 | 권장 판단 | 이유 |
|---|---|---|
| 구형 엔진·아카이브 감지 메시지 개선 | **우선 검토할 만함** | “알 수 없는 게임” 대신 감지 근거와 미지원 단계를 명확하게 보여 줄 수 있습니다. |
| 기존 MV/MZ 자산 처리의 비교시험 | **유용함** | 허용된 동일 샘플을 별도 작업본에서 처리하고 파일 목록·내용·실패 조건을 비교할 수 있습니다. 단, Decrypter 결과를 무조건 정답으로 삼아서는 안 됩니다. |
| XP/VX/VX Ace 완전 번역 지원의 출발 자료 | **장기 과제로는 유용함** | 아카이브 계층의 참고 자료는 되지만 데이터 번역 계층은 별도로 구현해야 합니다. |

반면 **Decrypter 실행 파일을 기본 의존성으로 추가하고 모든 RPG 처리를 우회시키는 방식은 권하지 않습니다.**

## 4. YSB Game Editor: Tsukuru에 더 직접적인 가치를 주는 부분

YSB는 Tsukuru보다 모든 면에서 상위인 도구라기보다, **Tsukuru의 강점과 다른 쪽에 기능이 집중된 도구**입니다. 특히 번역자가 판단할 수 있는 정보를 만드는 부분에서 참고할 가치가 큽니다.

### 4-1. 맵 대사·데이터베이스·플러그인 텍스트를 별도의 검수 대상으로 보여 주는 구조

YSB의 프로젝트 처리에는 맵 대사 외에 데이터베이스 가상 페이지와 플러그인 텍스트 페이지를 구성하는 코드가 있습니다. 플러그인 텍스트는 맵 대사·DB와 원본 컨테이너 및 저장 규칙이 다르기 때문에 별도 편집 계층으로 구분합니다. 화자 추론 결과도 출처별·화자별 집계로 저장합니다. 

이 발상은 Tsukuru에 잘 맞습니다.

지금의 추출 결과를 단순히 “번역해야 할 문자열 목록”으로만 보여 주기보다, **이 문자열이 어떤 종류의 텍스트인지에 따라 검수 화면을 다르게 구성**하는 것입니다.

예를 들어 다음은 서로 다른 검수 기준이 필요합니다.

| 텍스트 종류 | 검수할 핵심 정보 |
|---|---|
| 대사 | 앞뒤 메시지, 화자, 선택지, 말투, 같은 장면 안의 일관성 |
| 아이템·스킬 설명 | 명칭 통일, 수치·자리표시자 보존, 같은 DB 항목과의 연결 |
| 시스템 용어 | 메뉴 공간, 짧은 표현, 다른 화면과의 용어 일치 |
| 플러그인 매개변수·노트 | 실제 표시용 문자열인지, 식별자·조건식·경로인지, 안전하게 수정할 수 있는 위치인지 |

이것은 모든 플러그인 JavaScript 문자열을 번역하자는 제안이 아닙니다. **검수 대상으로 발견하는 것과 자동으로 수정하도록 허용하는 것은 분리해야 합니다.**

Tsukuru에는 이미 추출 분류와 원본 경로를 보존하는 manifest 구조가 있고, 플러그인 관련 추출 옵션과 경로 검사도 존재합니다. 따라서 새 파서를 무조건 늘리는 대신 기존 메타데이터를 사람이 이해하기 쉬운 검수 분류로 노출하는 것부터 시작할 수 있습니다.  

### 4-2. 문맥과 캐릭터 지침을 번역 요청에 함께 넣는 기능

YSB의 번역 엔진은 각 항목에 `id`, `text`, 선택적 `context`를 구성합니다. 여러 줄인 텍스트에는 줄 수와 줄 유지 지침도 넣습니다. 캐릭터별 지침은 묶음 안에서 중복을 제거하여 별도 프롬프트 블록으로 올리는 코드가 있습니다.   

Tsukuru에는 다음과 같이 반영하는 것이 좋겠습니다.

**문맥을 묶어서 읽되, 수정은 기존 개별 manifest ID로 되돌려 보내는 구조**입니다.

예를 들어 같은 메시지 블록의 대사를 함께 보여 주고 번역하게 하더라도, 결과를 적용할 때는 어떤 번역이 어떤 원본 항목에 대응하는지 유지해야 합니다. AI가 읽기 좋도록 블록을 합쳤다는 이유로 원래 행 수·이벤트 명령·들여쓰기를 임의로 재배치하면 안 됩니다.

이때 문맥의 기준은 편집된 TXT의 인접 행이 아니라 `Backup`이어야 합니다. Tsukuru의 기존 메시지 검사도 이미 이 원칙을 사용하므로, 해당 로직을 재사용하는 편이 좋습니다. 

화자 정보 역시 “확정된 화자”, “규칙으로 추정한 화자”, “알 수 없음”을 구분하는 것을 권합니다. 추정 정보를 정답처럼 모델에 넘기면, 문맥을 보강하려다가 잘못된 말투를 일관되게 만들어 낼 수 있기 때문입니다.

### 4-3. 용어집을 통째로 보내지 않고, 현재 문맥에 필요한 항목만 선택하는 기능

이 부분은 **구현 비용 대비 효과를 기대하기 좋은 참고점**입니다.

YSB는 용어집에서 사용자 지정 항목, 기존 수동 항목, DB 자동 추출 항목의 우선순위를 구분합니다. 현재 번역할 텍스트와 문맥에 등장한 용어만 선택하며, 긴 용어를 먼저 검사하고 선택 개수에도 제한을 둡니다. 

Tsukuru에 반영할 때는 기존 `translationDirectory`와 구분해야 합니다.

**현재 Tsukuru의 번역 사전은 “manifest ID → 해당 위치의 번역문”에 가깝습니다.** YSB식 용어집은 “게임 용어 → 권장 번역·사용 규칙”입니다. 둘은 이름이 비슷해도 역할이 다릅니다.  

권장하는 구분은 다음과 같습니다.

```text
위치별 번역 결과
  특정 manifest ID에 무엇을 적용할지 결정합니다.

용어집
  번역 제안을 만들 때 어떤 명칭과 표현을 사용할지 안내합니다.

검수 결과
  실제 번역문이 그 용어집과 일치하는지 확인합니다.
```

다만 YSB의 매칭 규칙도 그대로 정답으로 가져오면 안 됩니다. 긴 용어 안에 포함된 짧은 용어를 제외하는 방식은 유용하지만, 같은 묶음에 그 짧은 용어가 독립적으로도 등장하는 경우를 별도로 시험해야 합니다. 이는 확인한 매칭 코드에 근거한 경계 사례입니다. 

### 4-4. 실제 전송할 번역 요청을 미리 보여 주는 기능

YSB에는 `preview_translation_request()`가 있습니다. 시스템 프롬프트, 입력 항목, 캐릭터 지침, 정리된 문맥, 선택된 용어집을 **네트워크 요청 없이 확인할 수 있는 형태**로 구성합니다. 

이 기능은 Tsukuru의 에이전트 사용 방식에 특히 잘 맞습니다.

“번역 결과가 이상하다”는 문제가 생겼을 때, 결과문만 보는 대신 **모델에 실제로 무엇을 보냈는지** 확인할 수 있기 때문입니다. 도입한다면 번역 요청의 입력 ID, 원문 기준, 문맥, 용어집 버전, 선택한 제공자를 기록하고, API 키는 제외하는 방식을 권합니다.

이는 자동 번역 제공자를 여러 개 추가하는 것보다 먼저 구현해도 가치가 있습니다. 외부 모델을 호출하지 않고도, 준비된 번역 묶음의 품질을 사람이 검사할 수 있습니다.

### 4-5. 화면 미리보기는 유용하지만, “실제 게임과 동일한 실행 결과”는 아닙니다

YSB에는 고정된 게임 화면 좌표, 메시지 창 크기, 글꼴, 이름창·선택지 크기 등을 바탕으로 미리보기를 구성하는 설정과 렌더링 코드가 있습니다. 타일 분류·합성·진단 이미지 출력도 구현되어 있습니다. 글꼴은 원본을 수정하지 않고 캐시에 복사하거나, 필요한 경우 변환하여 로드합니다.   

하지만 다음 두 가지는 명확히 구분해야 합니다.

**첫째, `maker_runtime_preview.py`는 현재 빈 호환용 모듈입니다.** 이전 브라우저·런타임 캡처 경로가 제거되었다고 명시되어 있습니다. 파일이 존재한다는 이유로 “실제 RPG Maker를 실행하여 완벽하게 캡처하는 기능”으로 소개하면 틀립니다. 

**둘째, 일부 미리보기 설정은 실제 게임의 재현보다 번역자의 가독성을 우선합니다.** 예를 들어 그림을 번역자가 잘 볼 수 있도록 게임의 투명도 명령을 그대로 따르지 않는 기본 설정이 있습니다. 

Tsukuru에는 전체 맵 렌더러부터 이식하기보다, **메시지 창·화자명·선택지·글자 넘침 검사부터 추가하는 것**을 권합니다. 플러그인이 창 배치나 글꼴 동작을 변경하면 “미리보기 신뢰도 낮음”을 표시하고, 이를 실게임 검증 통과로 취급하지 않아야 합니다.

---

## 5. YSB에서 그대로 가져오면 안 되는 부분

좋은 기능과 별개로, 번역 엔진의 실패 처리와 상태 관리에는 Tsukuru의 기준으로 다시 설계해야 할 부분이 있습니다.

### 5-1. 번역 실패 시 원문을 반환하는 경로

`translate_text_batch()`는 묶음 번역이 실패하면 항목별로 다시 시도하고, 그마저 실패하면 원문을 결과에 넣습니다. 결과 수가 맞지 않을 때 원문을 추가하여 길이를 맞추는 처리도 있습니다. 

원문을 보존하는 것 자체는 유용합니다. 문제는 반환값이 문자열 목록이어서, **번역 성공과 실패 후 원문 보존을 결과만으로 명확하게 구분하기 어렵다는 점**입니다. 상위 UI가 이를 어떻게 표시하는지와 별개로, 이 엔진 인터페이스를 그대로 가져오는 것은 권하지 않습니다.

Tsukuru용으로는 항목별로 성공, 실패, 검수 필요, 의도적으로 유지한 원문을 분리해야 합니다. 번역되지 않은 원문을 “완료 항목”으로 계산하면 진행률과 품질 보고가 왜곡될 수 있습니다.

### 5-2. ID 검사는 있지만, 더 엄격한 응답 스키마가 필요합니다

YSB의 응답 파서는 누락 ID를 발견하면 오류를 내며, 결과 순서가 달라도 ID로 다시 정렬합니다. 이 부분은 참고할 만합니다.

그러나 `by_id` 딕셔너리에 값을 넣는 방식이어서 **중복 ID가 나오면 마지막 값으로 덮어쓰고**, 예상 밖 ID는 최종 결과를 만들 때 사용되지 않습니다. 번역문 필드도 엄격한 문자열 타입 검사보다는 문자열 변환에 의존합니다. 

도입안에서는 다음을 각각 검사하도록 권합니다.

| 응답 문제 | 권장 처리 |
|---|---|
| 누락 ID | 해당 묶음 또는 항목을 실패로 표시합니다. |
| 중복 ID | 마지막 값을 채택하지 말고 충돌로 처리합니다. |
| 예상하지 않은 ID | 정상 결과와 분리하여 오류로 보고합니다. |
| 잘못된 번역문 타입·허용되지 않은 빈 값 | 문자열로 강제 변환하지 말고 검증에서 거부합니다. |
| 요청 이후 원문·작업본이 바뀜 | 오래된 결과를 적용하지 않고 재검토 대상으로 돌립니다. |

### 5-3. 구형 로컬 번역 설정을 외부 제공자로 바꾸는 호환 정책

YSB에는 `local_argos`, `local_hf_jako`, `local_nllb` 등의 구형 설정값을 `openai`로 전환하는 호환 코드가 있습니다. **LM Studio의 현행 경로가 실패하면 무조건 외부로 전환된다는 뜻은 아닙니다.** 구형 설정값을 처리하는 별도 경로에 대한 관찰입니다.  

이 정책은 Tsukuru에 가져오지 않는 편이 좋습니다. 로컬 전용 작업을 선택했다면 연결 실패도 로컬 전용 실패로 끝나야 하고, 외부 제공자로의 전환은 별도 승인 대상이어야 합니다.

또한 확인한 Google 번역 경로는 원문 언어와 대상 언어가 일본어→한국어로 고정되어 있습니다. 현재 용도에 맞더라도 Tsukuru의 공통 제공자 인터페이스로 옮길 때는 명시적인 작업 설정으로 분리해야 합니다. 

### 5-4. Python GUI 구조 전체를 TypeScript 프로젝트로 가져올 이유는 없습니다

YSB에는 프로젝트 처리와 여러 UI mixin에 큰 구현이 집중되어 있고, 번역 설정도 전역 `Config`를 통해 공유됩니다. 반면 Tsukuru는 CLI·GUI가 공통 서비스와 검증 경계를 통과하도록 설계되어 있습니다.    

따라서 **기능의 개념과 데이터 처리 규칙은 참고하되, UI 구조·전역 상태·호환용 코드를 함께 옮기지 않는 것**이 좋겠습니다.

OCR·인페인팅도 마찬가지입니다. 관련 설정과 이름은 남아 있지만, 현재 번역 엔진에서는 호환용 스텁이며 실제 이미지 처리 호출은 지원하지 않는다고 명시합니다. 이것을 추가 AI 기능으로 계산해서는 안 됩니다.

## 6. Tsukuru에 반영한다면 권장하는 구조

핵심은 **YSB식 편집·번역 기능이 게임 파일을 직접 쓰는 두 번째 경로가 되지 않도록 하는 것**입니다.

Tsukuru의 RPG 적용 코드는 출력 트랜잭션을 만들기 전에 매핑·경로·Backup·manifest를 검사하고, 임시 출력에 적용한 뒤 결과 검증을 거쳐 반영합니다. 새 기능이 이 경로를 우회할 이유가 없습니다. 

아래는 현재 존재하는 명령을 나열한 것이 아니라, **제가 권하는 확장 구조**입니다.

```text
기존 Backup + manifest
        │
        ▼
문맥 인덱스 생성
원본 이벤트·DB·화자 근거·메시지 블록 정리
        │
        ▼
번역 요청 미리보기
원문·문맥·용어집·제공자 설정 확인
        │
        ▼
사람 또는 선택한 번역 제공자가 번역 제안 생성
게임 파일과 기존 Extract는 직접 수정하지 않음
        │
        ▼
검수 화면
원문/번역 비교·용어 일치·제어코드·표시 문제 확인
        │
        ▼
승인된 변경을 기존 manifest ID와 기대 해시에 연결
        │
        ▼
기존 patch → 기존 apply → 기존 출력 검증
```

### 6-1. 먼저 별도 문맥 파일을 추가하는 방식이 좋습니다

초기에는 기존 manifest를 크게 바꾸기보다, 예를 들어 `review-context.json` 같은 **별도 문맥 파일**을 두는 방식을 권합니다. 이름은 제안이며 현재 산출물이라는 뜻은 아닙니다.

여기에는 manifest ID, 원본 파일·위치, 메시지 블록, 이벤트·페이지, 화자와 그 근거, 문맥 생성 버전 등을 기록하면 됩니다. 중요한 것은 **원본 문맥의 기준과 현재 수정 대상 텍스트의 상태를 구분하는 것**입니다.

문맥은 `Backup`과 추출 메타데이터에서 만들고, 적용 시에는 현재 작업본과 기대 해시가 맞는지 확인해야 합니다. 원본이나 매핑이 바뀌면 오래된 문맥·번역 제안을 그대로 재사용하지 않도록 설계하는 것이 좋습니다. 기존 manifest에는 이미 안정 ID, 원본 파일, 데이터 경로, 추출 위치, 해시를 담을 구조가 있습니다. 

### 6-2. YSB를 별도 프로그램으로 쓰는 연동도 가능하지만, 즉시 호환은 아닙니다

YSB도 작업용 게임 복사본과 프로젝트 상태를 관리하며, 편집 중 상태와 저장을 구분하는 코드가 있습니다. 따라서 “YSB는 원본에 무작정 덮어쓰는 프로그램”이라고 평가하는 것은 부정확합니다.  

다만 **YSB의 편집 항목과 Tsukuru의 manifest ID가 자동으로 같은 대상을 가리킨다고 볼 근거는 없습니다.**

별도 앱 연동을 택한다면 교환 어댑터가 필요합니다. 맵 파일, 이벤트, 페이지, 명령 위치, DB 필드 등의 근거로 대응시키고, 원문이 일치하는지도 검사해야 합니다. 동일한 문자열이 여러 곳에 등장한다면 단순 문자열 일치로 연결해서는 안 됩니다.

특히 YSB에서 수정한 게임 JSON을 Tsukuru의 원본·Backup 대신 그대로 넣는 방식보다는, **번역 제안만 추출해 기존 patch 계약으로 가져오는 방식**을 권합니다.

### 6-3. 통일 번역도 “모든 같은 문자열을 치환”하지 않는 편이 좋습니다

YSB README가 제시하는 통일 번역·일괄 치환의 사용자 경험은 참고할 만합니다. 다만 Tsukuru에서 구현한다면, 동일 원문이라도 화자·장면·필드 종류가 다를 수 있다는 점을 반영해야 합니다. 

예를 들어 같은 짧은 응답이라도 선택지 문구와 인물의 대사는 다른 표현이 적절할 수 있습니다. 따라서 “후보 묶음 표시 → 적용 범위 선택 → ID별 변경 미리보기 → 기존 patch”의 흐름이 더 안전합니다.

## 7. 실제 개발 우선순위

구현 난도는 이번 코드 검토에 근거한 상대적 판단입니다. 성능 향상이나 번역 품질 상승을 수치로 측정한 결과는 아닙니다.

| 우선순위 | 반영할 기능 | 주로 연결할 기존 부분 | 상대 난도 | 완료 판단의 핵심 |
|---|---|---|---|---|
| **1** | 읽기 전용 문맥 인덱스와 검수 목록 | `manifest.ts`, `messageQuality.ts`, RPG 매핑 | 중간 | 다른 이벤트·페이지의 대사를 잘못 묶지 않고 원본을 변경하지 않습니다. |
| **2** | 용어집과 번역 요청 미리보기 | 별도 번역 준비 서비스 | 중간 | 사용자 용어 우선순위와 실제 선택된 문맥·용어를 확인할 수 있습니다. |
| **3** | 번역 제안 상태·재시도·이어하기 | 제공자 어댑터와 기존 `patch` | 중간~높음 | 실패·원문 유지·성공이 구분되고, 중복·누락·오래된 결과가 적용되지 않습니다. |
| **4** | 메시지 창·이름창·선택지 미리보기 | 검수 UI와 엔진별 표시 설정 | 중간~높음 | 실제 사용 글꼴과 창 폭을 반영하되, 미지원 동작을 성공으로 판정하지 않습니다. |
| **5** | 구형 엔진·아카이브 진단 강화 | 기존 감지·호환성 보고 | 낮음~중간 | 감지와 번역 지원을 분리하고 다음에 필요한 단계를 설명합니다. |
| **보류** | 전체 맵 렌더러·구형 엔진 완전 번역·외부 도구 전면 통합 | 신규 대규모 계층 | 높음 | 실제 대상 게임과 회귀시험 자료가 확보된 이후 범위를 정합니다. |

**첫 개발 묶음은 1번과 2번이 가장 좋겠습니다.** 자동 번역 제공자를 추가하지 않아도, 현재 작업팩을 더 잘 검수하고 기존 모델에 더 정확한 번역 입력을 전달할 수 있기 때문입니다.

그리고 실제 게임을 자동 실행하는 미리보기를 추가하기 전에는 별도의 선행 확인이 필요합니다. Tsukuru의 호환성 문서에는 실행 프로브의 사용자 Electron 프로필 환경 상속 문제가 과제로 기록되어 있습니다. 이 상태를 현재 HEAD에서 재확인하고 프로필·저장 데이터 격리를 검증한 뒤에 실행 기능을 확장해야 합니다. **정적 미리보기와 게임 실행 검증은 따로 진행하는 편이 맞습니다.** 

추가 기능의 공통 회귀시험에는 취소·오류 시 기존 출력 보존, 오래된 번역 결과 거부, 로컬 전용 모드의 외부 통신 차단, 문맥을 구할 수 없는 항목의 명시적 표시를 넣는 것을 권합니다. 새로운 검수 기능 때문에 기존 `recover`를 자동 호출하여 해시 불일치를 없애는 방식은 피해야 합니다. 저장소 문서도 해시 재구축과 의미 복구를 구분합니다.

## 8. 라이선스와 최종 판단

라이선스에서는 한 가지 주의할 점이 있었습니다. **YSB의 GitHub 메타데이터에는 `license: null`이 나오지만, README에는 소스 코드의 GPLv3 적용이 명시되어 있습니다.** GitHub 공식 문서도 라이선스 API가 README 등 다른 문서의 선언까지 반영하지 않는다고 설명합니다. 따라서 “라이선스가 없으니 재사용 불가” 또는 “아무 조건 없이 사용 가능”으로 판단하면 안 됩니다.   :chatgpt-content-reference{index="68"}

Tsukuru는 GPLv3, Decrypter는 MIT로 표시되어 있습니다. 일반적인 MIT/Expat 라이선스는 GPL과 호환되지만, 실제 도입에서는 가져온 코드의 저작권·라이선스 고지를 보존하고 배포 형태에 맞는 의무를 확인해야 합니다. YSB는 이름·로고를 공식판처럼 사용하는 권리까지 부여하는 것은 아니라고 별도로 명시합니다. 코드 포팅 시에는 원본 경로·커밋·변경 내용을 Tsukuru의 고지 문서에 기록하는 것을 권합니다.    :chatgpt-content-reference{index="72"}

마지막으로, Tsukuru 문서에 기록된 테스트 통과 수와 실제 작업팩 검사 결과는 **저장소에 남아 있는 검증 기록**이지 이번에 제가 재실행한 결과는 아닙니다. 세 도구의 번역 품질·속도·실게임 호환성에 대해 검증되지 않은 우열이나 개선율을 붙이지 않았습니다. 

**종합하면, Tsukuru가 지금 가장 크게 개선될 방향은 “더 많은 파일을 풀어내는 도구”가 아니라 “이미 안전하게 추출한 텍스트를 더 정확한 문맥으로 번역하고 검수하게 하는 도구”입니다.** YSB에서는 문맥 구성, 필요한 용어만 선택하는 용어집, 실제 번역 요청 미리보기, 메시지 표시 검수를 가져오고, Decrypter에서는 구형 포맷 이해와 비교시험 자료를 참고하는 구성이 좋습니다. 실제 파일 변경은 계속 Tsukuru의 기존 `patch → apply → 검증` 경로에 맡기는 것이 세 저장소의 장점을 가장 잘 결합하는 방법입니다.
