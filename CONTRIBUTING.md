# Contributing to Tsukuru Agent

Contributions should preserve source games, machine-readable contracts, and
rollback behavior. A feature is not complete when it only works through the GUI
or only succeeds on one local game.

## Reproduce the repository before editing

Use Node.js 22 or 24 and npm 10 or 11. From the application directory, run:

```powershell
cd tsukuru-agent
npm ci
npm run verify
```

Use `npm ci` for a clean review or release environment. Use `npm install` only
when intentionally changing dependency declarations or the lockfile. Do not
commit `.build`, `dist`, `dist-cli`, temporary workspaces, private corpus output,
or extracted game files.

## Add a failing test before changing behavior

Put tests under the responsibility that owns the boundary:

- `test/unit` for pure policy, parsing, and small lifecycle behavior;
- `test/contract` for JSON Schema, snapshots, inventories, CI, package, and
  documentation drift;
- `test/integration` for engine, archive, transaction, IPC, and filesystem
  boundaries;
- `test/e2e` for complete agent workflows and wrapper round-trips.

For mutation features, cover the successful path and at least one stale source,
hostile path or mapping, protected-file change, output conflict, and rollback
path. Assert that the original source hash is unchanged and that a failed
operation publishes no partial output.

## Build synthetic fixtures that can be published

Prefer small deterministic fixtures generated by test code. A fixture should
state its engine, wrapper, purpose, expected files, and canonical tree hash in
the fixture catalog. Keep binary structures minimal while preserving the exact
offset, length, encoding, or archive behavior under test.

Do not commit copyrighted games, personal paths, translation packs, tokens, or
private crash data. Real-game checks belong in the opt-in compatibility corpus
workflow. Public corpus results must remove absolute paths and identify manual
gameplay separately from structural verification.

## Change contracts deliberately

`schemaVersion` is a compatibility promise. When request, result, manifest, or
provenance fields change:

1. Update the canonical JSON Schema under
   `tsukuru-agent/src/core/contracts/schemas`.
2. Update static TypeScript contract types and runtime validation.
3. Add valid, invalid, unknown-option, and old-version tests.
4. Update checked-in examples and README snippets.
5. Add migration and deprecation notes before removing old behavior.

Do not reuse an existing field with a different meaning. Additive v2 changes
must still respect operation/format option discrimination. Read the
[v2 migration guide](tsukuru-agent/docs/contracts/v2-migration.md) and
[maintenance policy](docs/maintenance-policy.md) before changing a contract.

## Keep engine and container changes transactional

New engine support needs detection evidence, an engine capability entry,
manifest mapping, source snapshots, protected paths, structural validation, and
copy-only apply. New container support also needs bounded inspection, path and
link policy, provenance, required-entry checks, repack verification, and wrapper
preservation.

Experimental mutation must be default-disabled by a named v2 option, include a
diagnostic mode, and document its exact mutable subset. A flag cannot disable
unrelated integrity checks. Update the
[compatibility matrix](docs/compatibility.md) with Stable, Experimental,
Diagnostic, or Unsupported status.

## Update dependencies and generated policy together

For a runtime dependency change:

```powershell
npm install
npm run generate:notices
npm run check:supply-chain
npm audit --omit=dev
```

Update `docs/supply-chain/dependencies.json` with the exact locked version,
license, scope, and real import sites. External binaries and vendored assets
also require origin, license, size, SHA-256, and call-site inventory updates.
Major Electron or electron-builder changes must follow the documented
one-major-at-a-time ladder and rerun GUI, CLI, ASAR, NW.js, runtime-integrity,
and process-cleanup checks.

## Verify the complete change

Run the checks proportional to the affected boundary, then finish with:

```powershell
npm run verify
npm run test:order
npm run benchmark:check
```

On Windows, run `npm run test:electron` for GUI, preload, IPC, worker, settings,
or lifecycle changes. Package changes also require `npm run build:cli` followed
by `npm run verify:package`.

Documentation examples must be executable or schema-validated. Avoid test
counts in prose unless the inventory checker owns them. Add user-visible changes
to `CHANGELOG.md` and the current release notes.

## Prepare a release only after all gates pass

Follow the [release checklist](docs/release-checklist.md). It separates
automated evidence from manual gameplay and lists active release blockers. Do
not label structural verification or a short launch probe as a gameplay pass.
